# 复杂需求按需反构执行阶段

<!-- 阶段3b：复杂需求按需反构执行 -->

## 职责
执行复杂需求的按需反构流程：先产出"波及功能清单"供用户确认，再逐功能深入分析，最终生成汇总索引文档。每个功能的深入分析调用 `complex-on-demand-function-analyzer` 子 Agent。

## 适用场景

- 需求复杂、可能波及很多功能
- 需要先产出"波及功能清单"让用户确认，再逐功能深入分析
- 需要每个步骤都有中间缓存，便于复盘与增量迭代

## 核心约束（必须严格遵守）

- 🔴 **仅存量**：只描述"what exists"，不得把新需求当作已存在事实写入结论。
- 🔴 **证据优先**：所有结论必须能回溯到文档或代码定位；缺失则写"未提及/证据不足"，不得推断补全。
- 🔴 **步骤必须成功**：每个步骤必须执行成功，失败则终止流程并报告错误。
- 🔴 **路径一致**：所有输出必须写入同一个 `FEATURE_DIR`（绝对路径），不得重新计算或创建新的目录。
- 🔴 **路径根约束**：`FEATURE_DIR` 必须位于 `{REPO_ROOT}/changes/` 下；若检测到 `specs/` 或其他根目录，必须立即报错并终止流程。
- 🔴 **与 spec.md 解耦**：本阶段不依赖 `spec.md`，不得要求先创建或读取 `changes/<feature>/spec.md`。
- 🔴 **缓存优先**：执行前必须检查缓存，如果缓存存在且输入参数未变化，直接使用缓存结果，跳过重复执行。
- 🔴 **用户确认**：步骤5完成后必须等待用户确认波及功能与接口清单，确认后才能继续步骤6（启动双轨并行执行）。

## 输入（由主流程提供）

- `REPO_ROOT`（绝对路径，仓库根目录）
- `arguments`（用户原始输入）
- `constitution_path`（可选）
- `deep_architecture_result`（可选：建议为 `{REPO_ROOT}/omni-doc/on-demand/logic_architecture.md` 文件路径）

     - **数据链**：共享实体、消息体、数据库表、状态字段、缓存 key、配置项、模板/协议文件
     - **业务阶段链**：触发、执行、落库、汇总、上报、通知、补偿等阶段关系
   - 🔴 **逻辑架构增强扩散**：若 `deep_architecture_result` 中已识别出模块职责、上下游关系或主处理流程，则应将其作为候选扩散依据：
     - 命中某入口/分发模块后，补搜其在逻辑架构中的下游执行模块、结果消费模块、上报模块
     - 命中某业务阶段后，补搜逻辑架构中前后相邻阶段对应的模块、接口与资源
     - 命中某共享实体或配置后，补搜逻辑架构中读写该实体/配置的协同模块
   - 进行候选文档收集（文件名/标题/内容匹配）
   - 在支持 LSP 的语言中，**代码侧检索必须优先使用 LSP 工具**（如 `workspace/symbol`、`documentSymbol`）按函数名/类名/控制器名/服务名进行符号级检索，仅在 LSP 不可用时回退为 grep 等全文搜索
   - 使用 LSP 的符号信息识别控制器、服务类、入口 handler 等关键符号，并通过 `goToDefinition` 精确定位定义位置，避免整文件扫描

5.2. **独立执行静态配置/脚本/部署资产检索**：
   - 🔴 **强制要求**：本步骤为独立必执行步骤，不得并入 5.1 的源码检索结果后以“已覆盖”为由跳过
   - 🔴 **检索目标**：专门覆盖静态配置、脚本、部署、模板、协议、字典、资源清单等非源码资产
   - 重点目录至少包括：`scripts/`、`deploy/`、`deployment/`、`config/`、`configs/`、`charts/`、`helm/`、`manifests/`、`k8s/`、`resources/`
   - 检索时必须继续遵守“全文件检索、不按后缀限缩范围”的规则，但本步骤的分析重心应放在：
     - Deployment / StatefulSet / DaemonSet / Job / CronJob 等部署清单
     - Shell 脚本、启动脚本、渲染脚本、发布脚本
     - 环境变量、资源注解、挂载路径、参数文件、模板变量、配置 key
     - 资源配额、设备资源声明、路由/注册表/协议映射、默认值与回退值
   - 若需求关键词命中静态资产（如资源注解、环境变量、参数文件路径、模板变量），必须继续检查：
     - 该静态文件本体
     - 同目录相关成员
     - 生成/渲染/发布该文件的脚本
     - 消费这些配置的执行入口或运行时模块
   - 本步骤的产出必须并入候选波及清单，不能只作为旁路备注
   - 必须落盘：`{FEATURE_DIR}/on-demand/stage2-static-asset-scan.json`
   - 缓存内容至少包含：
     - 命中的静态资产文件列表
     - 每个文件的命中关键词
     - 关联的功能/接口/模块线索
     - 与源码或运行时入口的关联说明；若无法建立关联则写明“证据不足”

#### 波及功能分析强制补充步骤（🔴 与 5.1–5.3 一并遵守）

- 🔴 **核心目录完整文件清单**：一旦将某目录识别为核心分析范围，必须先对该目录执行 `ls` 或递归列出，形成**完整文件清单**并纳入分析视野，确保同目录下全部成员不遗漏。
- 🔴 **不得仅依赖文件名级命中结果**：禁止仅用 `grep -l`、`rg -l` 或等价“只返回文件名”的检索结果直接裁剪候选范围；对命中的核心目录，必须结合完整文件清单逐个复核，并查看匹配行、上下文或计数，避免遗漏同目录下命中但未在首轮列表中显式暴露的文件（尤其是 `util`、`constants`、默认值文件）。
- 🔴 **扩大搜索路径**：需求关联的实现与配置常跨多个目录；使用 grep 等全文检索时，检索范围须覆盖架构分层与模块边界所暗示的各层路径，以及架构/需求线索指向的路径，**禁止**在无证据的情况下将范围默认收窄为单一子树。
- 🔴 **默认使用全文件检索，不按后缀限缩范围**：全文检索默认必须覆盖候选目录中的所有文件类型，不得预设 `*.go`、`*.java`、`*.py`、`*.yaml` 等后缀过滤条件来缩小搜索面；只有在已有充分证据证明某类文件与需求无关时，才允许记录理由后做局部收敛。
- 🔴 **源码、脚本、配置、部署资源一体检索**：当需求线索涉及配置驱动、环境变量、部署清单、启动参数、资源注解、模板或协议时，必须将源码目录与 `scripts/`、`deploy/`、`deployment/`、`config/`、`configs/`、`charts/` 等目录放在同一轮全文件检索视野中，不得先按源码命中结果停止。
- 🔴 **按调用链与资源引用向下追溯**：当代码引用外部资源（配置、模板、数据或静态资源文件等）时，在定位到该引用后须**立即**检索该资源文件**所在目录**下的相关成员，并沿配置/资源依赖继续向下追溯一层或多层，将由此发现的项纳入候选波及范围与证据收集。
- 🔴 **按符号锚点继续追溯（防断链）**：当命中需求相关的全局变量、常量、枚举、静态 map key、注册表键等“符号锚点”时（即使它不是文件路径），也必须继续追溯，禁止在入口文件（如 `main.go`）停止。
  - 至少继续检查：符号定义位置、初始化与赋值位置、读取方、写入方、依赖该符号的分发逻辑/业务阶段、与该符号同组的相关常量或映射项。
  - 在支持 LSP 的语言中，优先使用 `goToDefinition`、`references`、`documentSymbol` 精确追踪符号链路；仅在 LSP 不可用时回退为全文检索。
  - 若符号命中后未继续追溯，必须记录为流程违规，不得将该分析结果标记为“已完成”。
- 🔴 **资源引用追踪检查清单**：命中配置、模板、数据或静态资源引用时，至少继续检查以下内容：
  - **引用点**：哪段代码读取/加载/拼装该资源，使用了哪些路径、key、文件名、模板名、schema 名称
  - **资源定义**：资源文件本体、结构定义、默认值、枚举项、占位符、字段说明
  - **同目录相关成员**：资源所在目录下的同类配置、模板片段、附属 schema、字典、索引文件
  - **读取方**：哪些模块、函数、任务、初始化逻辑会读取同一资源或同一组 key
  - **消费方**：哪些校验、分发、执行、落库、渲染、上报逻辑会消费该资源解析结果
  - **资源驱动逻辑**：由该资源决定的 handler 映射、消息类型分派、开关启停、规则判断、模板渲染、数据转换、上报出口
  - 若其中任一项命中需求相关线索，必须继续向下追踪至少一层，直至形成可回溯证据或确认“证据不足”
- 🔴 **按调度映射与业务阶段横向扩散**：遇到消息转发、事件分发、策略选择、任务编排等场景时，必须检查“键/类型/状态 -> 实现”的映射关系，以及其前后业务阶段（触发、执行、结果、上报/通知）对应的模块和文件，不能因为缺少直接函数调用而停止追踪。
- 🔴 **默认值/常量/参数文件专项补查**：若需求明确提到默认值、回退值、资源配额、环境变量或参数文件路径，必须额外检查核心模块及同目录下的 `util`、`constants`、`config`、`options`、`bootstrap`、`main` 等公共文件，并继续追踪这些常量或参数在脚本、配置和执行入口中的消费位置。
- **经典示例 1：消息转发型波及检索**：
  - 若需求命中“消息接口/消息转发/消息类型处理”，不得只停留在消息入口函数。
  - 必须继续检查：消息类型枚举/常量、路由键、分发函数、handler map 或 registry、最终处理函数、结果落库位置、上报/回调出口。
  - 典型断链修复：若在 `main.go` 命中 `SUCCL_GIDS` 这类全局变量，不得因“非路径引用”停止；必须沿 `SUCCL_GIDS` 的定义、赋值、引用和映射关系继续追到实际处理函数与上下游阶段。
  - 若分发关系由配置、schema、模板或字典驱动，还必须继续追踪这些资源及其读取方、消费方。
- **经典示例 2：巡检闭环型波及检索**：
  - 若需求命中“巡检/检查/探测/上报”之一，不得只检查单个执行函数。
  - 必须按业务阶段补查：触发入口（定时任务/事件/命令）、执行逻辑、结果落库或状态流转、结果聚合、上报/通知出口。
  - 若这些阶段通过共享表、状态字段、缓存 key、消息体或配置项串接，也应视为同一波及链路继续追踪。

5.3. **为每个候选功能项收集证据**：
   - 🔴 **强制要求**：每个候选功能项必须给出证据，若无法提供则标记为"证据不足"
   - 每个候选功能项必须给出证据：
     - 文档证据（路径/片段）或
     - 代码证据（文件路径 + 符号/入口定位）
   - 对非显式调用链场景，证据允许且应优先补充以下类型：
     - **调度证据**：消息类型、路由键、handler 映射、注册表项、策略选择分支
     - **数据证据**：共享实体、表名、状态字段、缓存 key、配置 key、模板/协议定义
     - **业务阶段证据**：触发器、定时任务、事件名、结果落库位置、上报/通知出口
     - **架构证据**：`deep_architecture_result` 中的模块职责、上下游模块关系、主处理流程节点（仅用于扩散与组织，不替代代码/文档存量证据）

     - 使用 `hover` 获取函数签名、参数/返回类型信息及紧邻的文档注释
     - 使用 `references` / 调用层级（call hierarchy）识别该符号的调用方/被调方，作为波及关系和入口线索的依据
   - 仅当 LSP 工具不可用或当前语言未接入 LSP 时，才允许通过 grep 等工具定位定义位置，并局部读取定义附近代码替代
   - 若无法提供证据，则标记为"证据不足"

5.4. **区分直接波及与间接波及**：
   - 🔴 **强制要求**：必须区分直接波及与间接波及
   - 直接波及：与需求关键词高度相关的功能/接口/模块描述
   - 间接波及：在文档中被直接波及项显式依赖/引用的项（未显式提及则不展开）
   - 在支持 LSP 的语言中，直接/间接波及的判断应优先基于 LSP 的 `references` / 调用层级（call hierarchy）结果：
     - 直接波及：需求关键路径或阶段2关键信息直接命中的函数/接口/模块本身
     - 间接波及：通过 LSP 调用关系识别"被直接波及项调用/依赖"的一层或有限层下游函数/模块（必须限制调用深度，避免无界展开）
   - 对非显式调用链场景，以下情况可判为直接波及：
     - 需求关键词直接命中的消息类型、路由键、状态字段、共享实体、配置项
     - 逻辑架构主流程中与需求场景直接对应的业务阶段模块
     - 明确承担“触发/分发/执行/上报”职责的核心模块
   - 对非显式调用链场景，以下情况可判为间接波及：
     - 被直接波及项通过映射表、注册表、共享数据或业务阶段显式关联的一层或有限层协同模块
     - 逻辑架构中与直接波及模块存在稳定上下游关系、且有代码或文档证据支撑的模块

   - **如果步骤 5.0 检测到已存在 `stage2-impact-confirmed.json` 且输入未变化，直接跳过此步骤，使用缓存结果**
  - 否则，**主动遍历** `stage2-impact-candidates.json` 与 `stage2-interface-candidates.json` 中的候选项，逐个向用户展示并获取确认：

            - 用户输入 "3" 或 "补充信息"：表示需要补充信息，随后应询问："请提供补充信息（功能描述/模块/入口等）："

          - **如果用户选择保留或补充了信息**：重新读取该功能对应的证据文件（文档路径/代码路径）

            - 如果用户补充了功能描述：在重新读取时验证描述是否与证据文件一致
            - 在支持 LSP 的语言中，重新分析代码证据时必须优先通过 LSP 工具完成：

              - 使用 `hover` 补齐或更新函数签名、类型信息与注释摘要
              - 使用 `references` / 调用层级更新调用关系（例如新增或修正入口/关联模块），仅在必要时局部读取实现代码
            - 基于重新读取（优先使用 LSP）的结果，更新功能信息（功能描述、模块、入口等）
