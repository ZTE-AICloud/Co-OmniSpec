# 接口详细分析 Skill（默认，精简版）

## Overview

这是一个**聚焦业务视角**的接口详细分析 Skill，用于针对**单个接口**梳理其完整业务功能与业务流程，并生成结构化的接口详细文档。  
Skill 重点描述接口的**业务价值、业务流程、参与的业务实体与输入输出约束**，弱化底层代码实现与具体技术细节。

## 输入参数（面向业务分析）

- **interface_info**（必需）
  - `interface_id`：接口唯一标识（如 `API_001`）
  - `name`：接口技术名称（如 `getUserInfo`）
  - `business_name`：接口业务名称（如“根据用户ID获取用户信息”）
  - `interface_type`：接口类型（RESTful API、RPC 接口、消息订阅、CLI 命令等）
  - `source_file`：接口所在文件路径（只作为定位入口使用）
  - `path_method`：接口访问标识（URL+方法 / Topic / 函数标识等）
  - 其他与业务相关的基础信息
- **template_path**（必需）：接口详情文档模板路径
- **output_dir**（必需）：接口详情文档输出目录
- **repo_root**（必需）：仓库根目录

## 输出结果

- **生成的接口详情文档**
  - 路径：`{output_dir}/{interface_id}_{中文业务简要总结}.md`
  - 文件名：`{接口ID}_{中文业务简要总结}.md`
  - 命名规范：`interface_id` 必须为 `API_001` 这类格式；后缀使用大模型生成的中文简要总结（不包含接口类型前缀），例如：`API_001_事务创建调度回调接口.md`

- **返回结果对象**

```json
{
  "status": "success" | "failed",
  "interface_id": "API_001",
  "output_file": "{output_dir}/API_001_事务创建调度回调接口.md",
  "error_message": null
}
```

含义说明：
- **success**：接口业务信息梳理完成，文档生成成功
- **failed**：关键输入缺失或文档生成失败，`error_message` 描述失败原因

## 业务流程视角的 Workflow

整个 Skill 从业务视角划分为四个主要步骤：

1. **读取模板（准备阶段）**
2. **分析接口业务信息（核心阶段）**
3. **填充模板并生成文档（输出阶段）**
4. **返回处理结果（收尾阶段）**

### 1. 读取模板（准备阶段）

**目标**：确保后续所有业务信息都有统一的承载结构。  

- 从 `template_path` 加载接口详情模板
- 检查模板是否存在、是否可读
- 如果模板出现问题（不存在 / 无法读取），直接判定为失败，返回明确的错误信息

### 2. 分析接口业务信息（核心阶段）

**核心目标**：围绕“这个接口在业务上到底做什么”进行全面梳理，而不是深入实现细节。  
分析维度主要包括：

- 接口基本信息（身份与角色）
- 业务功能与业务流程
- 入参（业务含义与约束）
- 出参（业务结果与异常情况）
- 访问入口（路径 / 方法 / 协议）
- 相关业务实体及关系

#### 2.1 接口基本信息（接口是谁）

- 从 `interface_info` 中提取：
  - 接口 ID、技术名称、业务名称
  - 接口类型（如“用户查询接口”“订单创建接口”等）
  - 所属模块 / 文件路径（用于说明接口归属的业务域）
- 在文档中明确“**接口定位**”：该接口属于哪个业务域、承担什么职责。

#### 2.2 业务描述与业务场景（接口在做什么）

**重点表达接口的业务价值与使用情境：**

- **业务描述**：这是什么接口？解决什么业务问题？
  - 例如：“根据用户 ID 查询用户基础资料和账户状态，用于前台展示或风控判断。”
- **功能说明**：接口做了哪些关键业务动作？
  - 如：校验输入 → 查询主数据 → 聚合多源信息 → 返回统一视图
- **使用场景**：
  - 由谁调用（前端应用、定时任务、第三方系统等）
  - 在什么业务流程节点被触发（如“用户登录后主页展示”“订单创建前风控检查”等）
- **约束条件**：
  - 调用前置条件（如“必须已登录”“必须具备某角色权限”）
  - 频率限制、数据范围限制等。

#### 2.3 业务流程分析（接口如何处理业务）

从业务流程角度描述接口内部大致处理步骤，而**不展开代码实现细节**。  
典型描述方式为：

- 1）**请求进入**：接收哪些关键字段，来源于哪里（终端、系统、任务等）
- 2）**前置校验**：对参数、权限、状态做哪些业务检查
- 3）**核心处理**：
  - 读取 / 修改哪些核心业务实体（如“用户”“订单”“支付记录”等）
  - 重要业务规则（例如“同一用户 24 小时内最多创建 N 笔订单”）
- 4）**外部交互**：是否调用外部系统或公共服务（用户中心、支付平台、消息服务等）
- 5）**结果构造**：最终对调用方暴露什么业务结果（成功、部分成功、失败分类等）
- 6）**后置动作**：是否有异步通知、日志落库、指标上报等后续处理。

输出应形成一段**可读性强的业务流程说明**，例如：

> “接口会根据传入的用户 ID 先校验用户是否存在及状态是否正常，然后从用户主数据与账户系统拉取用户基础信息与当前账户状态，最后拼装为统一视图返回给调用方，用于前台展示和后续业务决策。”

#### 2.4 参数业务含义与规则（请求端需要提供什么）

从调用者视角，说明“**要传什么、为什么要传**”：

- 列出每个关键参数：
  - 参数名
  - 业务含义（这个字段在业务上代表什么）
  - 是否必填、是否可选
  - 业务上的取值范围或规则（例如“必须为已有用户 ID”“金额必须大于 0”）
  - 与其他字段的关系（如“开始时间必须早于结束时间”）

目标是让业务方或接口调用方**不用看代码也能理解如何正确填写请求**。

#### 2.5 返回结果与业务状态（接口会返回什么）

从业务角度描述接口的**输出结构与可能的业务状态**：

- 正常返回时包含哪些业务信息：
  - 例如：“基础身份信息 + 账户状态 + 风险标记等”
- 关键字段的业务意义（而非字段类型）
- 典型成功响应示例（用自然语言说明结构即可，可选配合简化示例）
- 错误或异常场景：
  - 常见错误码（如“用户不存在”“权限不足”“业务规则不通过”等）
  - 每种错误代表的业务含义，以及调用方应如何处理（如“提示用户重新登录”“引导用户补全资料”）。

#### 2.6 访问入口与协议信息（如何访问接口）

- 对 REST 接口：
  - 说明 URL 路径、HTTP 方法
  - 是否有版本号（如 `/api/v1/users/{id}`）
- 对消息或事件接口：
  - 说明 Topic / Queue 名称
- 对内部服务调用：
  - 说明服务名、方法名以及调用约定（同步/异步等）

重点在于**接口的对外入口形态**，而不是具体路由实现方式。

#### 2.7 业务实体与关系（接口操作了哪些对象）

从领域模型视角梳理**接口直接或间接涉及的业务实体**：

- 列出关键业务实体（如“用户”“订单”“商品”“优惠券”等）
- 说明接口与这些实体的关系：
  - 只读查询 / 创建 / 更新 / 软删除等
  - 是否存在强关联（例如“订单必须关联有效用户和商品”）
- 简要描述主要实体的核心属性（只需要和当前接口紧密相关的部分）

目标是帮助读者理解：**这个接口站在业务域中，正在操作哪些核心对象，它们之间是什么关系**。

### 3. 填充模板并生成文档（输出阶段）

**目标**：将上述业务分析结果转化为**统一、可阅读、可交付**的接口详情文档。

- 按模板结构填充：
  - 接口基础信息区块
  - 业务描述与使用场景区块
  - 业务流程说明区块
  - 请求参数说明表格
  - 返回结果与错误码说明
  - 业务实体与领域关系说明
- 将生成内容写入 `{output_dir}/{interface_id}_{中文业务简要总结}.md`
- 如果输出目录不存在，需要创建后再写入。

### 4. 返回处理结果（收尾阶段）

- 当文档成功生成且内容完整时：
  - 返回 `status = "success"`，附带 `interface_id` 与 `output_file` 路径
- 当任一关键步骤失败（如模板缺失、无法写文件等）时：
  - 返回 `status = "failed"`，并在 `error_message` 中说明失败原因

调用方只需要根据 `status` 和 `error_message` 即可判断本次接口业务文档是否生成成功。

## 错误处理与质量要求（业务视角）

- **模板或输出目录问题**：直接终止并返回失败，提示“模板不存在/不可读/输出路径不可写”等业务可读信息。
- **接口信息不完整**：例如缺少 `interface_id` 或 `business_name` 时，应返回失败，并在错误信息中指明缺失字段。
- **业务信息提取不充分**：在无法完全获取某些信息时，可以在文档中标记为“待补充/未识别”，但应尽可能保证整体结构完整。
- **质量要求**：
  - 文档结构完整、可阅读
  - 业务流程描述清晰，能帮助读者理解接口在**业务链路中的位置与作用**
  - 接口 ID、文件名、文档内容中的标识保持一致
