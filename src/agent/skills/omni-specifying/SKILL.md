# omni-specifying

本技能对应 `/omni.specify` 命令, 下文基本为**原命令说明的原文**, 仅作为技能文档直接复用, 不对内容做额外改写或拆分。

## 用户输入

```text
$ARGUMENTS
```

在继续之前, 你**必须**考虑用户输入(如果不为空).

## 概述

用户在触发消息中 `/omni.specify` 后输入的文本**就是**功能描述. 假设你始终可以在本次对话中访问它, 即使下面字面上显示 `$ARGUMENTS`. 除非用户提供了空命令, 否则不要要求用户重复.

基于该功能描述, 执行以下操作:

**注意**: 此命令会自动执行上下文收集和规范生成的完整流程. 它会扫描反构文档、计算关联度、构建关联关系图、进行架构分析, 生成上下文中间态文件, 然后基于上下文生成功能规范.

1. **创建特性分支**

2. **获取文档目录配置**（在加载上下文之前执行）:
   - 判断当前操作系统，windows还是linux系统;
   - 针对不同操作系统从仓库根目录运行脚本获取配置
     windows:`.specify/scripts/powershell/check-prerequisites.ps1 --json --paths-only`
     linux:`.specify/scripts/bash/check-prerequisites.sh --json --paths-only`
   - 解析 JSON 输出获取 **DOC_DIR** 变量（如果未设置则默认为 "omni-doc"）
   - **重要**: DOC_DIR 将用于后续所有文档路径引用，支持通过环境变量 `SPECIFY_DOC_DIR` 或 `.specify/config` 文件配置

4. **需求波及分析**（生成上下文中间态文件）:

5. **加载上下文**:
   - 读取 `.specify/templates/spec-template.md` 和 `.specify/memory/constitution.md`
   - **读取上下文文件**:
     * 读取步骤4生成的 `FEATURE_DIR/context.md` 作为上下文参考
     * 如果上下文文件不存在（异常情况），可以基于功能描述直接生成规范(不使用上下文)

6. 遵循此执行流程:

    1. 从输入解析用户描述
       如果为空: 错误 "未提供功能描述"
    2. 参考上下文文件 (`FEATURE_DIR/context.md`) 中的架构分析、可复用模式、术语对齐等信息
    3. 从描述和上下文中提取关键概念
       识别: 参与者、操作、数据、约束
    4. 对于不明确的方面: 
       - 基于上下文和行业标准做出有根据的猜测
       - 仅在以下情况下标记为 [NEEDS CLARIFICATION: 具体问题]: 
         - 选择显著影响功能范围或用户体验
         - 存在多个合理的解释且有不同的含义
         - 没有合理的默认值
       - **限制: 最多 3 个 [NEEDS CLARIFICATION] 标记**
       - 按影响优先级排序: 范围 > 安全/隐私 > 用户体验 > 技术细节
       - 优先参考上下文文件中的约束和假设
    5. 生成/更新功能需求(规范的「需求」章节)
       - **需求定义**: 从系统视角出发, 描述系统应具备的能力和行为(回答"系统能做什么/如何响应"), 而非具体用户使用步骤
       - **需求与场景关系**: 一个需求可以对应多个用户场景; 场景用于体现价值与验证需求
       - **描述格式(EARS)**:
         * 主句: 系统 shall [能力描述]
         * 条件子句:
           - When [触发事件], 系统 shall [系统响应]
           - While [特定状态], 系统 shall [系统响应]
           - If [异常条件], 系统 shall [系统响应]
           - Where [可选特性], 系统 shall [系统响应]
       - **相关文档**: 从 `FEATURE_DIR/context.md` 的 `相关需求文档` 获取候选需求文档列表, 优先在其上做变更
       - **动作类型判断**(对每条需求):
         * MODIFY: 现有需求需要修改才能满足用户描述(优先修改相关需求文档)
         * INSERT: 无法归属到任何相关需求文档, 需要新增需求
         * DELETE: 除非有不得不删除的理由, 否则不要删除(必须删除时说明理由与影响)
         * REFER: 相关需求文档已满足用户描述, 不做修改(但作为波及分析与后续关联参考)
       - **变更标记规则**:
         * 修改/新增的片段使用 `**加粗**`
         * 删除的片段使用 `~~删除线~~`
       - **需求ID生成规则(仅 INSERT 时)**:
         * 扫描 `DOC_DIR/specs/requirements/` 下所有 `REQ-XXX-*.md`
         * 提取已有需求ID(REQ-001, REQ-002, ...)
         * 取最大编号 + 1 作为新ID(即使中间缺号也按最大递增)
       - **可测试性**: 每个需求必须可验证/可测试; 未指定细节用合理默认值并在规范中显式记录(必要时用 [NEEDS CLARIFICATION] 标记)
    6. 生成/更新用户场景与测试(规范的「用户场景与测试」章节)
       - **场景定义**: 从终端用户视角用简洁、非技术化语言描述"谁需要/为什么需要/需要什么"
       - **场景描述格式**: 作为<用户角色>, 我希望<完成某个操作>, 以便<实现某个价值/达成某个目标>
       - **相关文档**: 从 `FEATURE_DIR/context.md` 的 `相关场景文档` 获取候选场景文档列表, 优先在其上做变更
       - **动作类型判断**(对每个场景): 同需求章节的 INSERT/MODIFY/DELETE/REFER 规则, 变更标记同样使用加粗/删除线
       - **场景ID生成规则(仅 INSERT 时)**:
         * 扫描 `DOC_DIR/specs/scenarios/` 下所有 `SCN-XXX-*.md`
         * 提取已有场景ID并取最大编号 + 1
       - **优先级**: 为每个场景分配 P1/P2/P3(按用户价值与重要性排序); 将每个场景视为独立的功能切片, 可以独立开发/测试/部署/演示
       - **归属的需求**:
         * INSERT: 将场景归属到本规范中某个需求ID, 并记录在场景条目中
         * MODIFY/DELETE/REFER: 读取 `DOC_DIR/specs/relations/requirements.json`, 在 JSON 数组中查找 `targets` 包含当前场景ID的条目, 该条目的 `source` 即关联需求ID
       - **验收场景**: 使用 Given/When/Then 列出至少 2 条可验收的行为, 覆盖主路径与关键异常/边界
       - 如果无法形成明确的用户流程与验收: 错误 "无法确定用户场景"
    7. 定义成功标准
       创建可衡量的、技术无关的结果
       包括定量指标(时间、性能、数量)和定性措施(用户满意度、任务完成)
       每个标准必须无需实现细节即可验证
    8. 识别关键实体(如果涉及数据)
       参考上下文文件中的逻辑实体文档
    9. 返回: 成功(规范准备好进行规划)

7. 使用模板结构将规范写入 SPEC_FILE, 用从功能描述(参数)和上下文文件派生的具体细节替换占位符, 同时保持章节顺序和标题.

8. **规范质量验证**: 编写初始规范后, 根据质量标准进行验证:

   a. **创建规范质量检查清单**: 加载`.specify/templates/requirements-template.md`获取`验证项目模版`信息，使用`验证项目模版`在 `FEATURE_DIR/checklists/requirements.md` 生成检查清单文件

   b. **运行验证检查**: 根据每个检查清单项目审查规范:
      - 对于每个项目, 确定是否通过或失败
      - 记录发现的具体问题(引用相关规范章节)

   c. **处理验证结果**:

      - **如果所有项目都通过**: 标记检查清单完成并继续步骤 9

      - **如果项目失败(不包括 [NEEDS CLARIFICATION])**:
        1. 列出失败的项目和具体问题
        2. 更新规范以解决每个问题
        3. 重新运行验证直到所有项目都通过(最多 3 次迭代)
        4. 如果 3 次迭代后仍然失败, 在检查清单备注中记录剩余问题并警告用户

      - **如果 [NEEDS CLARIFICATION] 标记仍然存在**:
        1. 从规范中提取所有 [NEEDS CLARIFICATION: ...] 标记
        2. **限制检查**: 如果存在超过 3 个标记, 仅保留 3 个最关键的(按范围/安全/用户体验影响)并为其余部分做出有根据的猜测
        3. 对于每个需要的澄清(最多 3 个), 以以下格式向用户呈现选项:

           ```markdown
           ## 问题 [N]: [主题]

           **上下文**: [引用相关规范章节]

           **我们需要了解**: [来自 NEEDS CLARIFICATION 标记的具体问题]

           **建议答案**:

           | 选项 | 答案 | 含义 |
           |--------|--------|--------------|
           | A      | [第一个建议答案] | [这对功能意味着什么] |
           | B      | [第二个建议答案] | [这对功能意味着什么] |
           | C      | [第三个建议答案] | [这对功能意味着什么] |
           | 自定义 | 提供你自己的答案 | [解释如何提供自定义输入] |

           **你的选择**: _[等待用户响应]_
           ```

        4. **关键 - 表格格式**: 确保 markdown 表格格式正确:
           - 使用一致的间距, 管道符对齐
           - 每个单元格内容周围应有空格: `| 内容 |` 而不是 `|内容|`
           - 标题分隔符必须至少有 3 个破折号: `|--------|`
           - 测试表格在 markdown 预览中正确渲染
        5. 按顺序编号问题(Q1、Q2、Q3 - 最多 3 个)
        6. 在等待响应之前一起呈现所有问题
        7. 等待用户响应所有问题的选择(例如, "Q1: A, Q2: 自定义 - [详情], Q3: B")
        8. 通过用用户选择或提供的答案替换每个 [NEEDS CLARIFICATION] 标记来更新规范
        9. 在所有澄清解决后重新运行验证

   d. **更新检查清单**: 每次验证迭代后, 使用当前的通过/失败状态更新检查清单文件

9. 报告完成情况, 包括分支名称、上下文文件路径、规范文件路径、检查清单结果以及下一阶段(`/omni.clarify` 或 `/omni.design`)的准备就绪状态.

**注意**: 
- 上下文收集会在规范生成之前自动执行，生成 `FEATURE_DIR/context.md` 文件
- 规范生成会参考上下文文件中的架构分析、可复用模式、术语对齐等信息

## 通用指南

## 快速指南

- 专注于用户需要**什么**和**为什么**.
- 避免如何实现(不涉及技术栈、API、代码结构).
- 为业务利益相关者编写, 而不是为开发者.
- 不要创建嵌入规范中的任何检查清单. 那将是一个单独的命令.

### 章节要求

- **必需章节**: 每个功能必须完成
- **可选章节**: 仅在与功能相关时包含
- 当章节不适用时, 完全删除它(不要保留为 "N/A")

### AI 生成

当从用户提示创建此规范时: 

1. **做出有根据的猜测**: 使用上下文、行业标准和常见模式来填补空白
2. **记录假设**: 在假设章节中记录合理的默认值
3. **限制澄清**: 最多 3 个 [NEEDS CLARIFICATION] 标记 - 仅用于关键决策: 
   - 显著影响功能范围或用户体验
   - 存在多个合理的解释且有不同的含义
   - 缺乏任何合理的默认值
4. **优先澄清**: 范围 > 安全/隐私 > 用户体验 > 技术细节
5. **像测试人员一样思考**: 每个模糊的需求都应该在"可测试且明确"的检查清单项目上失败
6. **NEEDS CLARIFICATION 的常见领域**(仅在没有合理默认值时): 
   - 功能范围和边界(包含/排除特定用例)
   - 用户类型和权限(如果可能存在多个冲突的解释)
   - 安全/合规要求(当具有法律/财务重要性时)

**合理默认值的示例**(不要询问这些): 

- 数据保留: 该行业的行业标准实践
- 性能目标: 标准 Web/移动应用期望, 除非另有说明
- 错误处理: 用户友好的消息和适当的回退
- 认证方法: Web 应用的标准基于会话或 OAuth2
- 集成模式: RESTful API, 除非另有说明

### 成功标准指南

成功标准必须是: 

1. **可衡量的**: 包括具体指标(时间、百分比、计数、速率)
2. **技术无关的**: 不提及框架、语言、数据库或工具
3. **以用户为中心的**: 从用户/业务角度描述结果, 而不是系统内部
4. **可验证的**: 无需了解实现细节即可测试/验证

**好的示例**: 

- "用户可以在 3 分钟内完成结账"
- "系统支持 10,000 个并发用户"
- "95% 的搜索在 1 秒内返回结果"
- "任务完成率提高 40%"

**坏的示例**(以实现为中心):

- "API 响应时间在 200ms 以下"(太技术化, 使用"用户立即看到结果")
- "数据库可以处理 1000 TPS"(实现细节, 使用面向用户的指标)
- "React 组件高效渲染"(框架特定)
- "Redis 缓存命中率超过 80%"(技术特定)
