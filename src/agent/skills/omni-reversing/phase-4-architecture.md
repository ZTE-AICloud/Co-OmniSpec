# 阶段 4：分析逻辑架构

## 输入内容
`omni-doc/specs-temp/intermediate/entity-overview.md`

**输入文件格式说明**：
- 输入文件为Markdown格式，包含"实体列表"概要表格和"实体详情"段落
- 每个实体详情包含：实体ID（格式为 `ENTITY-XXX`）、实体名称、描述、属性表格、方法表格
- 需要从实体概览中分析实体关系、数据流向和业务流程

## 步骤

### 第一步：理解输入内容
仔细阅读输入内容，关注：
- 所有逻辑实体的描述
- 逻辑实体的属性列表（属性表格）
- 逻辑实体的方法列表（方法表格）

### 第二步：实体分类
根据实体的描述和方法表格中的方法名，识别实体的功能类型。常见的实体类型包括但不限于：

- **核心资源实体**：管理业务领域核心资源的实体，通常具有完整的生命周期（创建、更新、删除、查询），并需要与外部系统同步状态
- **通信实体**：处理系统间通信的实体，负责消息构造、协议转换、请求发送等通信相关功能
- **服务实体**：提供系统级服务的实体，如监控、对账、配置管理等跨领域服务功能
- **配置实体**：管理配置信息的实体，提供配置的查询、更新等功能
- **辅助资源实体**：支持核心资源实体的辅助性资源，如规则、策略、端口等

### 第三步：架构层次划分
基于实体分类结果，划分系统的架构层次：

1. **识别层次边界**：根据实体的职责和依赖方向，确定层次划分
2. **定义层次名称和职责**：为每个层次命名，并说明该层的核心职责
3. **实体归层**：将每个实体分配到对应的架构层次中
4. **验证层次合理性**：确保层次间的依赖方向一致（上层依赖下层），避免循环依赖

### 第四步：关系识别
分析实体之间的关系，包括但不限于：

- **管理关系**：上层组件（插件/驱动/服务）管理下层资源实体
- **包含关系**：资源实体之间的层次包含关系，父资源包含子资源
- **关联关系**：资源实体之间的引用关系，通过ID或引用字段关联
- **依赖关系**：资源创建或操作时的依赖关系
- **同步关系**：资源实体通过通信实体与外部系统进行状态同步
- **组合关系**：多个资源实体组合形成复合资源，强耦合
- **聚合关系**：多个资源实体聚合，但可独立存在

### 第五步：绘制逻辑架构图
使用PlantUML的 `package` 和 `component` 语法，**按架构层次组织**：
- 使用 `!define` 为每个层次定义颜色（LAYER1_COLOR, LAYER2_COLOR...）
- 使用 `package` 按层次组织实体，层次内可嵌套子包
- 每个实体标注名称和实体ID（格式：`实体名称\nENTITY-XXX`）
- 使用 `<<LAYERX>>` 标签为实体分配层次颜色
- 包含所有逻辑实体，不遗漏
- 关系标注使用业务语义（如"管理"、"调用"、"依赖"）

### 第六步：架构逻辑实体说明
按架构层次逐实体输出详细说明：
- **实体ID**：`ENTITY-XXX`
- **逻辑实体职责**：实体的核心职责和主要功能
- **主要接口**：实体提供的主要接口或服务
- **依赖关系**：实体依赖的其他逻辑实体或资源

### 第七步：数据流向分析
识别数据在实体之间的流转路径，按业务流程结构化输出：
- 每条业务流程独立一节
- 每条流程包含：**输入**（来源和内容）→ **处理路径**（编号步骤，标注经过的实体和操作）→ **输出**（内容和去向）
- 通过方法调用链识别流转路径
- 通过方法参数和返回值识别数据传递方向

### 第八步：核心业务机制说明
根据当前系统业务特征，按机制独立子节输出：
- 每个机制独立一个三级标题（如：生命周期管理、消息分发机制、配置管理、错误处理、状态同步等）
- 每个机制下按具体子项展开说明
- 仅输出代码中实际存在的机制，不虚构

### 第九步：补充可选章节
根据代码分析结果，酌情补充以下可选章节（有则写，无则省略）：
- **设计原则**：系统的设计理念和架构决策
- **技术栈**：通信协议、框架/库、数据存储、开发语言
- **扩展性设计**：水平扩展、功能扩展、接口扩展
- **约束与限制**：性能限制、资源限制、并发限制等

### 第十步：整理输出
读取模板文件 `specify/metamodel/4.logic-architecture-template.md`，严格按照模板结构生成输出文件：
- 存放到 `omni-doc/specs/logic_architecture.md`
- 确保 YAML frontmatter 中所有字段填写完整（name, version, description）
- 确保输出格式符合Markdown规范

### 第十一步：DoD 校验
生成文档后，执行以下校验，全部通过方可结束本阶段：

1. **实体全覆盖**：从 `entity-overview.md` 的"实体列表"表格提取所有 `ENTITY-XXX` ID，逐一确认在架构图（PlantUML component 图）和"架构逻辑实体说明"章节中均出现
2. **Frontmatter 完整性**：`name`、`version`、`description` 字段均非空
3. **章节结构**：对照模板 `specify/metamodel/4.logic-architecture-template.md`，确认必选章节全部存在
4. **PlantUML 语法**：架构图代码块有 `plantuml` 语言标识，且无明显语法错误（如括号不闭合、缺少 `@enduml`）
5. **层次无循环依赖**：检查架构图中的依赖箭头方向，确认不存在循环依赖路径
6. **数据流向完整**：至少包含 1 条以上的业务流程路径描述

如果发现问题，就地修复后重新校验，直到全部通过。

## 分析要点
- **完整性**：确保所有逻辑实体都包含在架构分析中，不遗漏任何实体
- **准确性**：关系识别必须基于实体的字段和方法定义，不能主观推测
- **清晰性**：架构图层次清晰，关系明确，便于理解系统结构

## 输出格式

读取模板文件 `specify/metamodel/4.logic-architecture-template.md`，严格按照模板结构生成输出文件。

### 输出要求
- **输出路径**：`omni-doc/specs/logic_architecture.md`
- **模板遵循**：文件结构、frontmatter 字段、章节层级均以模板文件为准
- **填充规则**：
  - 将分析步骤中提取的信息填充到模板对应位置
  - frontmatter 中所有字段必须填写完整（name, version, description）
  - 架构图按层次组织，使用层次颜色体系（LAYER1/LAYER2/...）
  - 架构逻辑实体说明按层次分组，逐实体展开
  - 数据流向按业务流程结构化
  - 核心业务机制按机制独立子节
  - 可选章节有则写、无则省略

## 注意事项
1. 根据实体概览文件中的实际内容生成，不要虚构实体或关系
2. 关系识别要基于方法名和字段名中的实际调用关系
3. 保持组件图的简洁性，避免过于复杂的嵌套
4. 架构图颜色按层次分配，非按实体类型分配
5. 添加必要的注释，说明关键的业务逻辑和设计决策
