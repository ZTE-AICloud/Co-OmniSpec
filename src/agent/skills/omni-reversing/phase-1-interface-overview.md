# 阶段 1：识别接口

## 输入内容
`omni-doc/specs-temp/intermediate/project-entry.md`

**输入文件格式说明**：
- 输入文件为Markdown格式，包含项目入口点信息
- 每个入口包含：入口文件、交互方式、交互标识等信息
- 需要从入口文件中识别所有对外接口

## 步骤
### 第一步：理解输入内容
仔细阅读输入内容，关注：
- 所有入口文件
- 对外交互方式
- 对外交互的实现映射

### 第二步：识别接口
1. **对每个入口文件单独分析**：
   - 根据入口文件的**对外交互方式**（如函数回调、REST API、RPC、消息队列、事件驱动等），识别所有接收外部请求的接口
   - 识别**外部系统→当前系统**的交互场景（即处理外部需求的场景）
   - 排除**当前系统→外部系统**的主动调用场景（这不是我们要识别的对外接口）
   - 参考 `analyse-project-entry.md` 中的交互方式分类和具体实现分析方法

2. **基于模式匹配查找遗漏接口**：
   - 分析已找到的所有**对外交互入口标识**（如消息号前缀、API路由模式、回调函数命名规则等）
   - 提取共同特征和命名模式（例如：`MSG_XXX_REQ`、`/api/v1/*`、`on_*_callback`等）
   - 使用grep等工具在代码库中搜索符合这些模式的其他接口
   - 验证搜索结果是否为真实的外部请求入口，避免误报
   - 补充初次分析时遗漏的对外接口

3. **接口定义与映射**：
   - 将每一个**处理外部请求的实现**定义为一个独立接口
   - 每个接口应包含：接口入口标识（消息号/API路径/回调函数等）和对应的处理代码位置
   - 确保接口粒度适中：既是完整的业务处理单元，又不过于复杂

### 第三步：接口ID分配
为识别出的每个接口分配唯一ID：
- ID格式：`API-001`、`API-002`、`API-003`...（后缀数字顺序递增）
- ID规则建议：
  * 相关接口的ID尽量连续（如启动、更新、停止）
  * 主流程接口ID靠前，辅助接口ID靠后
- 记录接口ID与接口名称的对应关系

### 第四步：接口入口标识识别
对每个接口，明确其触发入口作为接口入口标识：

1. **消息驱动接口**：
   - 查找消息号/事件号（如 `EV_ACTL_TO_ACC_START_REQ`）
   - 确认消息来源（哪个外部系统）
   
2. **RESTful API接口**：
   - 识别RESTful路径（如 `/api/v1/sessions`）
   - 确认HTTP方法（GET、POST、PUT、DELETE）
   - 分析路由配置和端点定义
   
3. **定时器接口**：
   - 查找定时器配置和触发条件
   - 确认定时器类型（周期性、一次性）
   
4. **回调接口**：
   - 识别回调注册函数
   - 确认回调触发条件

根据接口入口标识，找到该接口的处理代码，并记录代码映射信息：
- 使用grep工具搜索相关函数名或消息号
- 追踪调用链路
- 记录接口处理代码所在文件的相对路径
- 记录处理函数/方法名，对于面向对象的代码记录为`[类/对象]::[方法名]`格式，对于非面向对象的代码直接记录函数名

### 第五步：遗漏接口补全
1. 根据已找到的接口入口标识，提取相同的特征，进行grep搜索查找
2. 逐项检查`project-entry.md`所有入口文件，确认是否已全部检索

### 第六步：接口描述撰写
为每个接口撰写清晰的描述：
- **接口名称**：简洁明了，体现业务含义
- **接口描述**：1-3句话描述接口的业务目的和处理内容
- **关键信息**：涉及的外部系统、消息流向、主要处理逻辑

### 第七步：整理输出
按照**输出格式**，整理所有接口信息：

1. **接口分类**：
   - 按照业务功能边界区分，将所有识别出的接口聚合分类

2. **生成接口概览文件**：
   - 存放到`omni-doc/specs-temp/intermediate/interface-overview.md`
   - 统计接口总数
   - 按照分类结果以表格形式列出所有接口信息
   - 表格包含：接口ID、接口名称、接口描述、入口标识、所在文件、代码映射

### 第八步：概览 DoD 校验
生成概览文件后，执行以下自闭环校验，全部通过方可结束本阶段：

1. **ID 唯一性**：所有 `API-XXX` ID 无重复
2. **ID 连续性**：ID 序列基本连续（允许少量跳号，不应大段缺失）
3. **表格字段完整性**：每行的 6 个字段（接口ID、接口名称、接口描述、入口标识、所在文件、代码映射）均非空
4. **入口覆盖**：逐项比对 `project-entry.md` 中的所有入口文件，确认每个入口文件至少有一个接口对应
5. **代码映射可达**：抽样验证 3-5 个接口的"所在文件"路径确实存在、"代码映射"中的函数/方法在文件中可找到
6. **Markdown 格式**：表格语法正确、无断行错位

如果发现问题，就地修复后重新校验，直到全部通过。

## 分析要点
- **完整性**：确保所有入口文件中的接口都已识别，不遗漏任何接口
- **准确性**：接口识别必须基于代码实际内容，不能主观推测
- **可追溯性**：每个接口都要明确对应的代码位置和入口标识

## 输出格式
### **接口概览文件格式** (`interface-overview.md`)
```markdown
# 接口概览

## 接口统计
- **接口总数**：[接口数量]
- **接口分类数**：[分类数量]

## 接口列表

### [接口类别1]

| 接口ID | 接口名称 | 接口描述 | 入口标识 | 所在文件 | 代码映射 |
|--------|----------|----------|----------|----------|----------|
| API-001 | [接口名称] | [接口描述，1-3句话] | [入口标识，如消息号、RESTful路径等] | [文件相对路径] | [类/对象]::[处理函数/方法名] 或 [处理函数] |
| API-002 | [接口名称] | [接口描述，1-3句话] | [入口标识] | [文件相对路径] | [类/对象]::[处理函数/方法名] 或 [处理函数] |
| ... | ... | ... | ... | ... | ... |

### [接口类别2]

| 接口ID | 接口名称 | 接口描述 | 入口标识 | 所在文件 | 代码映射 |
|--------|----------|----------|----------|----------|----------|
| API-010 | [接口名称] | [接口描述，1-3句话] | [入口标识] | [文件相对路径] | [类/对象]::[处理函数/方法名] 或 [处理函数] |
| ... | ... | ... | ... | ... | ... |

**说明**：
- **接口ID**：唯一标识符，格式为 `API-XXX`
- **接口名称**：简洁明了的业务名称
- **接口描述**：1-3句话描述接口的业务目的和处理内容
- **入口标识**：触发接口的入口标识，如消息号（如 `EV_ACTL_TO_ACC_START_REQ`）、RESTful路径（如 `POST /api/v1/sessions`）、回调函数名等
- **所在文件**：接口处理代码所在文件的相对路径，如 `networking_zte/ml2/ml2_neutron_driver.py`
- **代码映射**：
  - 对于面向对象的代码：格式为 `[类/对象]::[处理函数/方法名]`，如 `ML2NeutronDriver::create_network()`
  - 对于非面向对象的代码：直接使用 `[处理函数]`，如 `create_network()`
```
