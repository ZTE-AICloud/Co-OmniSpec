# omni-design-modeling

从功能规范（`spec.md`）出发，系统化完成技术设计建模的核心产出：逻辑实体分析、功能定义、数据模型设计、接口契约定义。

## 输入

- **用户参数**：`$ARGUMENTS`（通常为 IMPL_DESIGN 模板路径或设计主文档路径，用于写入逻辑实体/功能章节）
- **前置文件**（由调用方或 FEATURE_DIR 提供）：
  - `spec.md`：功能规范
  - `context.md`：相关反构文档列表（REQ/SCN/FUNC/API/ENTITY）
  - `research.md`：技术未知项已解决
  - 逻辑架构文档：`${DOC_DIR}/specs/logic_architecture.md` 或项目约定的 `doc/specs/logic_architecture.md`

## 输出

- **写入 $ARGUMENTS 的章节**：`逻辑实体`、`功能`
- **生成文件**：`FEATURE_DIR/data-model.md`、`FEATURE_DIR/contracts/api-contract.md`、`FEATURE_DIR/quickstart.md` 等
- **参考模板**：`.specify/templates/data-model-template.md`、`.specify/templates/interface-template.md`

## 指令

### 步骤 1: 分析逻辑实体

**输入**：
- `spec.md`：功能需求和场景
- `doc/specs/logic_architecture.md`：系统分层架构
- `context.md`：`相关逻辑实体文档`章节

**分析方法**：
1. 以 `logic_architecture.md` 的分层为基准，定位本需求影响的层级与边界
   
2. 以 `spec.md` 的需求/场景/约束为依据，识别需要变更的逻辑实体
   
3. 对每个受影响逻辑实体，确定动作类型：
   - **MODIFY**：优先修改 `相关逻辑实体文档` 指向的逻辑实体
     - 仅描述变更的内容（`实体结构`、`属性说明`、`方法说明`）
     - 未变更的内容不需要展示
     - 职责未变化则省略 `职责说明` 章节
   
   - **INSERT**：当需求无法归属于现有实体时新增
     - 实体ID生成规则：扫描 `doc/specs/logic_entities/ENTITY-XXX-*.md`，找到最大编号后递增
     - 确定实体所在层次，在 `职责说明` 中描述与其他实体的关系
   
   - **DELETE**：除非有充分理由，否则不删除
     - 必须删除时，给出理由和影响分析
   
   - **REFER**：现有实体已满足需求，仅作参考
     - 用于后续波及分析

4. 对每个实体输出：
   - 责任边界（In/Out of scope）
   - 关键职责（做什么、不做什么）
   - 与其它逻辑实体的协作关系（同层协作/跨层调用方向）
   - 关键状态/属性（只写与需求有关的）

**输出位置**：
- 写入 $ARGUMENTS 模板的 `逻辑实体` 章节

### 步骤 2: 定义功能

**输入**：
- 步骤1的逻辑实体分析结果
- `spec.md` 中的用户场景与测试部分
- `context.md` 中的`相关功能文档`章节

**功能定义**：
- 单个逻辑实体提供的能力；或不同层级间逻辑实体合作完成的能力
- 功能要可落地：能映射到“谁来做 + 输入/输出 + 触发条件/前置条件 + 主要步骤 + 失败与补偿”
- 禁止把“实现细节/代码结构”当功能；禁止把“接口列表”当功能

**分析方法**：
1. 将 `spec.md` 中的用户场景拆分为独立功能模块
   
2. 与 `context.md` 中的相关功能文档对比，确定动作类型：
   - **MODIFY**：现有功能需要修改才能满足需求
     - 优先修改相关功能文档
     - 变更内容用 **加粗** 表示
     - 删除内容用 ~~删除线~~ 表示
   
   - **INSERT**：需求无法归属于现有功能时新增
     - 功能ID生成规则：扫描 `doc/specs/functions/FUNC-XXX-*.md`，找到最大编号后递增
   
   - **DELETE**：除非有充分理由，否则不删除
     - 必须删除时，给出理由和影响分析
   
   - **REFER**：现有功能已满足需求，仅作参考

3. 对每个功能输出：
   - 来源于哪个场景
   - 归属逻辑实体（主责方）与协作方（如有）
   - 所在层级与跨层调用链路（如有）
   - 输入/输出（抽象到领域数据，不先绑定具体接口）
   - 优先级（P1/P2/P3），P1 是最关键的

**输出位置**：
- 写入 $ARGUMENTS 模板的 `功能` 章节

### 步骤 3: 生成数据模型

**输入**：
- 步骤1的逻辑实体分析结果
- `spec.md` 中的验证规则和约束

**分析方法**：
1. 从逻辑实体中识别核心数据结构
   - 数据结构名称、字段、关系
   - 来自需求的验证规则
   - 状态转换（如适用）

2. 对每个数据结构输出：
   - 定义（代码形式，如 C 结构体、类定义等）
   - 关键字段（字段名、类型、描述）
   - 验证规则（必填、格式、范围等）
   - 状态转换（如有状态机）
   - 代码映射（文件路径、结构体/类名）

3. 描述数据结构之间的关系
   - 组合关系、引用关系、继承关系等

**输出位置**：
- 生成文件：`FEATURE_DIR/data-model.md`
- 参考模板：`specify/templates/data-model-template.md`

### 步骤 4: 生成接口契约

**输入**：
- 步骤1的逻辑实体分析结果（特别是方法说明）
- `context.md` 中的`相关接口文档`章节

**分析方法**：

#### 4.1 对外接口

对外接口指所有接收外部请求的接口：
- 识别**外部系统→当前系统**的交互场景
- 排除**当前系统→外部系统**的主动调用场景

1. 查看 `context.md` 中的 `相关接口文档` 章节

2. 确定动作类型：
   - **MODIFY**：现有接口需要修改才能满足需求
     - 优先修改相关接口文档
   
   - **INSERT**：需求无法归属于现有接口时新增
     - 接口ID生成规则：扫描 `doc/specs/interfaces/API-XXX-*.md`，找到最大编号后递增
   
   - **DELETE**：除非有充分理由，否则不删除
     - 必须删除时，给出理由和影响分析
   
   - **REFER**：现有接口已满足需求，仅作参考
     - 给出引用理由 + 文档定位（文件路径/章节/锚点）
     - 无需重复粘贴契约全文

3. 对每个接口输出：
   - 变更原因
   - 来源逻辑实体（ENTITY-XXX）
   - 接口定义（函数签名或接口定义代码）
   - 接口描述（主要功能和处理逻辑）
   - 调用场景（触发条件、调用者、调用时机）
   - 输入参数（参数类型和说明）
   - 返回值（返回值类型和说明）
   - 处理流程（文字描述或流程图）
   - 代码映射（可选：实现函数、所在文件、调用关系）

#### 4.2 内部接口

内部接口包括系统内部模块间的接口：
- 函数调用接口：函数签名、参数、返回值
- 消息传递接口：消息类型、消息结构、处理流程
- 事件驱动接口：事件标识符、事件数据、触发条件
- 其他接口

对每个内部接口输出与对外接口相同的信息（除了接口ID）。

**输出位置**：
- 生成文件：`FEATURE_DIR/contracts/api-contract.md`
- 参考模板：`specify/templates/interface-template.md`

## 关键原则

### 单一职责
- 每个逻辑实体只负责一个明确的业务领域
- 功能定义要可落地，能映射到具体的实现步骤

### 分层约束
- 严格遵循 `logic_architecture.md` 中的分层规则
- 明确跨层调用的方向和边界

### 优先复用
- 优先 MODIFY 现有的 REQ/SCN/FUNC/API/ENTITY 文档
- 只有在无法归属时才 INSERT 新文档
- 避免不必要的 DELETE 操作

### 映射一致性
- 逻辑实体的方法应对应接口契约
- 逻辑实体的属性应对应数据模型
- 功能应对应用户场景

### 代码映射
- 尽可能提供代码映射信息
- 帮助实施阶段快速定位代码位置
