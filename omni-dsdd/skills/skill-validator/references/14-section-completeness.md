# 1. 章节完整性检查

章节完整性检查确保技能文档包含所有必需的章节和内容，符合规范要求并提供完整的信息。

## 1.1 必需章节检查

### 1.1.1 概述章节检查
- [ ] **必须包含概述章节** [必选项]：确保技能有明确的概述部分
  - 验证方法：扫描包含 'Overview'、'概览' 或 '职责与输入输出' 的标题
  - 章节要求：
    - 使用 ## 标题级别
    - 包含职责说明
    - 包含输入前提说明
    - 包含输出产物说明
  - 错误示例：缺少概述章节或概述过于简单
  - 正确示例：
    ```markdown
    ## 概览（职责与输入输出）

    ### 职责
    本技能负责分析和重构代码架构...

    ### 输入前提
    - 用户提供代码路径
    - 代码位于 Git 仓库中
    - 环境已配置必要工具

    ### 输出产物
    - 架构分析报告
    - 重构建议列表
    - 优化后的代码结构
    ```
  - 自动修复：否

### 1.1.2 概述内容完整性
- [ ] **概述章节应包含职责说明** [必选项]
  - 验证方法：检查概述章节中是否有职责相关的标题或内容
  - 内容要求：
    - 清晰说明技能的主要职责
    - 明确技能的适用范围
    - 说明技能的价值和目的
  - 错误示例：概述章节缺乏职责说明
  - 正确示例：
    ```markdown
    ### 职责
    本技能负责自动化代码重构工作，包括：
    - 分析现有代码结构
    - 识别重构机会
    - 执行安全的重构操作
    - 验证重构结果
    ```
  - 自动修复：否

### 1.1.3 概述章节输入输出说明
- [ ] **概述章节应包含输入输出说明** [必选项]
  - 验证方法：检查概述章节中是否有输入输出相关的内容
  - 内容要求：
    - 明确说明技能的输入参数
    - 说明前置条件
    - 明确描述输出结果
    - 说明可能的副作用
  - 错误示例：概述章节缺乏输入输出说明
  - 正确示例：
    ```markdown
    ### 输入前提
    - 用户提供有效的代码路径
    - 代码文件可读可写
    - Git 工作区干净（无未提交的更改）

    ### 输出产物
    - 重构后的代码文件
    - 重构日志和报告
    - Git 提交记录（如果执行了提交）
    ```
  - 自动修复：否

## 1.2 阶段总览检查

### 1.2.1 阶段总览章节检查
- [ ] **多阶段 skill 必须包含阶段总览章节** [必选项]
  - 验证方法：如果 skill 描述了多个阶段，扫描是否包含 '阶段总览' 或 'Phase Overview' 标题
  - 检查条件：
    - skill 包含 3 个或更多阶段
    - 有阶段描述但缺少总览
  - 错误示例：多阶段 skill 缺少阶段总览
  - 正确示例：
    ```markdown
    ## 阶段总览

    本技能分为以下 4 个阶段：

    ### 阶段 1：需求分析
    分析用户需求，确定重构范围和目标...

    ### 阶段 2：代码分析
    深入分析现有代码结构...

    ### 阶段 3：重构执行
    执行具体的重构操作...

    ### 阶段 4：验证测试
    验证重构结果和功能完整性...
    ```
  - 自动修复：否

### 1.2.2 阶段总览内容完整性
- [ ] **阶段总览应列出所有阶段及简要描述** [必选项]
  - 验证方法：检查阶段总览是否包含所有阶段
  - 内容要求：
    - 列出所有阶段
    - 为每个阶段提供简要描述
    - 说明阶段的执行顺序
    - 说明阶段间的依赖关系
  - 错误示例：阶段总览不完整或描述过于简单
  - 正确示例：
    ```markdown
    ## 阶段总览

    本技能按顺序执行以下 4 个阶段：

    1. **需求分析**（预计 5-10 分钟）
       - 分析用户需求和代码路径
       - 确定重构范围和目标
       - 生成重构计划

    2. **代码分析**（预计 10-15 分钟）
       - 分析代码结构和依赖关系
       - 识别重构机会
       - 生成分析报告

    3. **重构执行**（预计 20-30 分钟）
       - 按计划执行重构操作
       - 保持代码功能不变
       - 记录所有变更

    4. **验证测试**（预计 10-15 分钟）
       - 运行测试套件
       - 验证功能完整性
       - 生成验证报告

    各阶段依次执行，前一阶段成功完成后才开始下一阶段。
    ```
  - 自动修复：否

## 1.3 复杂技能管理检查

### 1.3.1 Cache/Todo/Token 管理指导检查
- [ ] **复杂 skill 应包含 Cache/Todo/Token 管理指导** [可选项]
  - 验证方法：对于 3+ 阶段的 skill，扫描是否有关于 cache、todo 或 token 管理的章节
  - 检查条件：
    - skill 包含 3 个或更多阶段
    - 没有明确的管理指导
  - 错误示例：复杂技能缺乏管理指导
  - 正确示例：
    ```markdown
    ## 上下文管理

    ### 缓存策略
    - 在阶段 1 收集的代码结构信息会在后续阶段重用
    - 避免重复分析相同的代码文件
    - 使用文件变更时间戳判断缓存有效性

    ### Todo 集成
    - 使用 TodoList 工具跟踪各阶段的进度
    - 每个阶段完成后标记对应的任务为完成状态
    - 中间结果通过任务描述在不同阶段间传递

    ### Token 预算
    - 总预算：100K tokens
    - 阶段 1（需求分析）：10K tokens
    - 阶段 2（代码分析）：30K tokens
    - 阶段 3（重构执行）：40K tokens
    - 阶段 4（验证测试）：20K tokens
    - 如接近预算上限，使用更简洁的输出格式
    ```
  - 自动修复：否

### 1.3.2 阶段间数据传递说明
- [ ] **多阶段 skill 应说明阶段间的数据传递方式** [必选项]
  - 验证方法：检查是否有阶段间数据传递的说明
  - 内容要求：
    - 说明哪些数据需要在不同阶段间传递
    - 说明传递的方式（变量、文件、任务等）
    - 说明数据的格式和结构
  - 错误示例：多阶段技能缺乏数据传递说明
  - 正确示例：
    ```markdown
    ## 阶段间协作

    ### 数据传递方式
    1. **阶段 1 → 阶段 2**
       - 通过 TodoList 传递重构计划
       - 任务描述包含重构清单和优先级

    2. **阶段 2 → 阶段 3**
       - 通过临时文件 `analysis_results.json` 传递分析结果
       - 文件包含代码结构图和重构建议

    3. **阶段 3 → 阶段 4**
       - 通过 Git 状态传递变更信息
       - 验证阶段检查实际的代码变更
    ```
  - 自动修复：否

## 1.4 错误处理章节检查

### 1.4.1 错误处理章节检查
- [ ] **复杂 skill（3+ 阶段）应包含错误处理章节** [可选项]
  - 验证方法：对于 3+ 阶段的 skill，扫描包含 'Error Handling'、'错误处理' 或 '错误恢复' 的标题
  - 检查条件：
    - skill 包含 3 个或更多阶段
    - 没有明确的错误处理说明
  - 错误示例：复杂技能缺乏错误处理说明
  - 正确示例：
    ```markdown
    ## 错误处理

    ### 阶段 1 错误处理
    - **输入验证失败**：提示用户提供正确的代码路径
    - **文件访问错误**：检查文件权限和路径有效性
    - **超时情况**：设置合理的分析超时时间

    ### 阶段 2 错误处理
    - **语法错误**：跳过包含语法错误的文件，继续分析其他文件
    - **内存不足**：分批处理大文件，减少内存占用
    - **分析超时**：限制单个文件的分析时间

    ### 阶段 3 错误处理
    - **重构失败**：回滚所有变更，保留原始状态
    - **依赖冲突**：跳过导致冲突的重构，记录到报告
    - **语法破坏**：立即停止重构，恢复备份

    ### 阶段 4 错误处理
    - **测试失败**：提供详细的失败报告和修复建议
    - **回归问题**：识别引入的问题，回滚相关变更
    - **测试超时**：标记为警告，完成其他测试
    ```
  - 自动修复：否

### 1.4.2 恢复策略说明
- [ ] **错误处理章节应包含恢复策略** [必选项]
  - 验证方法：检查是否有恢复策略的说明
  - 内容要求：
    - 说明错误后的恢复方式
    - 说明哪些操作可以重试
    - 说明哪些操作需要手动干预
    - 说明回滚机制
  - 错误示例：只有错误描述，缺乏恢复策略
  - 正确示例：
    ```markdown
    ### 恢复策略

    **自动恢复**：
    - 临时文件访问错误：重试 3 次，间隔 1 秒
    - 网络请求失败：使用指数退避策略重试
    - 分析超时：减少分析深度，快速完成

    **手动干预**：
    - 代码结构过于复杂：提供分析报告，建议人工分析
    - 重构冲突：提供冲突详情和建议解决方案
    - 测试失败：提供详细的失败日志和修复指导

    **回滚机制**：
    - Git 回滚：使用 `git checkout --` 恢复未提交的变更
    - 文件备份：执行重构前自动创建 `.backup` 文件
    - 状态检查：每个阶段开始前验证前阶段的状态
    ```
  - 自动修复：否

## 1.6 章节组织合理性检查

### 1.6.1 章节顺序合理
- [ ] **章节顺序应符合逻辑** [可选项]
  - 验证方法：检查章节的顺序安排
  - 推荐顺序：
    1. 概览（职责与输入输出）
    2. 执行流程或阶段总览
    3. 详细的阶段说明（如有）
    4. 上下文管理（复杂技能）
    5. 错误处理（复杂技能）
    6. 使用示例（如有）
    7. 参考文档
  - 错误示例：章节顺序混乱，不符合逻辑
  - 正确示例：章节按照从概述到细节的顺序排列
  - 自动修复：否

### 1.6.2 章节层级合理
- [ ] **章节层级应清晰合理** [可选项]
  - 验证方法：检查标题的层级使用
  - 层级要求：
    - H1 (#)：通常只有一个，主标题
    - H2 (##)：主要章节
    - H3 (###)：子章节
    - H4 (####)：细节说明
    - 避免跳级使用
  - 错误示例：从 H2 直接跳到 H4
  - 正确示例：按顺序使用 H1 → H2 → H3 → H4
  - 自动修复：否
