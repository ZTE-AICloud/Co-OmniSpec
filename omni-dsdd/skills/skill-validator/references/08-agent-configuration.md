# 1. 子代理配置检查

子代理配置（context: fork 和 agent）用于控制技能的执行环境，合理的配置能够提高技能的性能和安全性。

## 1.1 子代理必要性检查

### 1.1.1 context: fork 使用场景
- [ ] **长时间运行任务配置 fork** [可选项]：长时间运行的任务应使用子代理
  - 验证方法：分析任务的执行时间
  - 长时间任务示例：
    - 大规模代码库分析
    - 复杂的依赖关系分析
    - 深度代码重构
    - 全面的架构审查

- [ ] **高复杂度任务配置 fork** [可选项]：高复杂度的任务应使用子代理
  - 验证方法：分析任务的复杂度
  - 高复杂度任务示例：
    - 多步骤工作流
    - 需要多次迭代的任务
    - 涉及多个文件/模块的任务
    - 需要深度搜索和分析的任务

- [ ] **需要隔离的任务配置 fork** [可选项]：需要隔离上下文的任务应使用子代理
  - 验证方法：检查任务是否需要隔离
  - 需要隔离的场景：
    - 避免污染主会话上下文
    - 保护主会话的内存使用
    - 隔离工具权限
    - 避免干扰主会话的工作

### 1.1.2 不需要 fork 的场景
- [ ] **简单任务不使用 fork** [可选项]：简单任务不应使用子代理
  - 验证方法：检查任务复杂度
  - 简单任务示例：
    - 单文件修改
    - 简单代码生成
    - 快速信息查询
    - 基础代码解释

- [ ] **短时间任务不使用 fork** [可选项]：短时间任务不应使用子代理
  - 验证方法：估计任务执行时间
  - 短时间任务：
    - 执行时间 < 1分钟
    - 单次操作
    - 少量文件处理
    - 简单逻辑判断

## 1.2 agent 配置检查

### 1.2.1 agent 类型有效性
- [ ] **agent 类型在系统支持范围内** [必选项]：使用支持的代理类型
  - 验证方法：对照支持的代理列表检查
  - 常用代理类型：
    - `Explore`：代码库探索
    - `Plan`：方案设计
    - `general-purpose`：通用任务
    - `claude-code-guide`：Claude Code 使用指导
    - Omni 系列：`omni-dsdd:*` 特定功能代理

- [ ] **agent 类型匹配任务性质** [必选项]：代理类型应与任务性质匹配
  - 验证方法：分析任务需求
  - 代理类型匹配：
    - 代码探索 → `Explore`
    - 方案设计 → `Plan`
    - 通用任务 → `general-purpose`
    - 功能识别 → `omni-dsdd:function-identifier`

### 1.2.2 agent 配置完整性
- [ ] **context: fork 时必须指定 agent** [必选项]：使用 fork 时必须指定代理类型
  - 验证方法：检查 context: fork 时是否有 agent 字段
  - 错误示例：
    ```yaml
    ---
    context: fork
    # 缺少 agent 字段
    ---
    ```
  - 正确示例：
    ```yaml
    ---
    context: fork
    agent: Explore
    ---
    ```

### 1.2.3 agent 配置合理性
- [ ] **agent 配置有明确说明** [可选项]：子代理配置应有使用说明
  - 验证方法：检查文档中是否有说明
  - 错误示例：使用子代理但无任何说明
  - 正确示例：
    ```markdown
    ## 子代理说明

    本技能使用 `Explore` 子代理来：
    1. 深度探索代码库结构
    2. 分析代码依赖关系
    3. 识别关键模块和功能

    使用子代理可以：
    - 隔离主会话上下文
    - 提高分析效率
    - 避免内存占用过大
    ```

### 1.2.4 skill 调用 subagent 方式检查

本节检查skill通过各种方式调用subagent的完整性和规范性，包括调用方式、参数传递、返回值处理、错误处理等全方位验证。

##### 7.2.4.1 调用方式明确性检查

- [ ] **调用方式明确且统一** [必选项]：skill文档中明确说明使用哪种方式调用subagent
  - 验证方法：搜索"调用"、"subagent"、"Agent"、"TaskCreate"等关键词
  - 支持的调用方式：
    1. **Agent工具调用**：使用Agent工具直接调用
    2. **TaskCreate任务调用**：使用TaskCreate创建任务
    3. **Bash命令调用**：通过Bash执行命令行调用
    4. **references/scripts脚本调用**：调用脚本中的subagent实现
  - 错误示例：文档中提到"调用subagent"但未说明具体方式
  - 正确示例：
    ```markdown
    ## 子代理调用方式

    本阶段使用 **Agent工具** 调用 Explore 子代理：
    - 调用工具：Agent
    - 子代理类型：Explore
    - 传递参数：通过prompt参数传递任务描述
    ```

- [ ] **Agent工具调用规范** [必选项]：使用Agent工具时符合规范
  - 验证方法：检查Agent工具的调用方式
  - 必需参数：
    - `subagent_type`：子代理类型（必需）
    - `prompt`：任务描述（必需）
    - `description`：简短描述（必需，3-5个词）
  - 可选参数：
    - `model`：模型覆盖
    - `run_in_background`：后台运行
    - `isolation`：隔离模式（worktree）
  - 错误示例：缺少必需参数或参数值错误
  - 正确示例：
    ```markdown
    使用Agent工具调用Explore子代理：
    - subagent_type: Explore
    - prompt: "分析代码库中的接口定义，识别所有API接口"
    - description: "分析代码库接口定义"
    ```

- [ ] **TaskCreate任务调用规范** [必选项]：使用TaskCreate时符合规范
  - 验证方法：检查TaskCreate工具的调用方式
  - 必需参数：
    - `subject`：任务标题（必需）
    - `description`：任务描述（必需）
  - 可选参数：
    - `activeForm`：进行时态的活动形式
    - `metadata`：元数据
  - 错误示例：缺少必需参数
  - 正确示例：
    ```markdown
    使用TaskCreate创建子任务：
    - subject: "分析接口定义"
    - description: "从代码库中识别所有接口定义并生成清单"
    - activeForm: "正在分析接口定义"
    ```

- [ ] **Bash命令调用规范** [必选项]：通过Bash调用时符合规范
  - 验证方法：检查Bash命令的调用方式
  - 命令要求：
    - 命令可执行且路径正确
    - 参数传递格式正确
    - 有输出重定向或日志记录
    - 有超时设置
  - 错误示例：硬编码路径、无错误处理、无超时
  - 正确示例：
    ```markdown
    通过Bash调用Python脚本：
    ```bash
    python3 /path/to/script.py --input file.json --output result.json > logs/script.log 2>&1 &
    echo $! > logs/script.pid
    ```

- [ ] **references/scripts脚本调用规范** [必选项]：调用脚本时路径正确
  - 验证方法：检查脚本路径的设置
  - 路径优先级：
    1. 优先：`{REPO_ROOT}/.claude/skills/{skill-name}/referencess/scripts/`
    2. 次选：`{REPO_ROOT}/claude/skills/{skill-name}/referencess/scripts/`
  - 错误示例：硬编码绝对路径、路径不存在
  - 正确示例：
    ```markdown
    调用脚本时按优先级查找：
    1. 先检查 `.claude/skills/reverse-interfaces/referencess/scripts/`
    2. 如不存在，再检查 `claude/skills/reverse-interfaces/referencess/scripts/`
    ```

##### 7.2.4.2 参数传递检查

- [ ] **Agent工具prompt参数规范** [必选项]：prompt参数传递符合规范
  - 验证方法：检查prompt参数的格式和内容
  - prompt要求：
    - 清晰的任务描述（3-5句话）
    - 明确的输入说明
    - 明确的输出要求
    - 必要的上下文信息
  - 错误示例：prompt过于简短或模糊
  - 正确示例：
    ```
    prompt: "分析以下代码文件中的接口定义。输入文件位于 {file_list}。
           识别所有函数接口，提取接口名、参数、返回值等信息。
           输出JSON格式的接口清单，包含接口ID、名称、位置等字段。"
    ```

- [ ] **TaskCreate subject/description规范** [必选项]：TaskCreate参数传递符合规范
  - 验证方法：检查subject和description参数
  - subject要求：
    - 简洁的任务标题（动宾结构）
    - 字数控制在50字以内
  - description要求：
    - 详细的任务说明
    - 包含输入、输出、约束条件
  - 错误示例：subject过长或description过于简短
  - 正确示例：
    ```
    subject: "分析接口定义并生成清单"
    description: "从代码库中识别所有接口定义。输入为扫描范围内的源代码文件列表。
                输出为JSON格式的接口清单。需遵循接口识别规范，确保接口类型正确。"
    ```

- [ ] **Bash命令行参数规范** [必选项]：Bash命令参数传递符合规范
  - 验证方法：检查命令行参数的格式
  - 参数要求：
    - 使用标准参数格式（--key=value 或 -k value）
    - 特殊字符正确转义
    - 文件路径使用引号包裹
    - 敏感信息通过环境变量传递
  - 错误示例：参数格式错误、路径未加引号
  - 正确示例：
    ```bash
    python3 script.py \
      --input "/path/to/input.json" \
      --output "/path/to/output.json" \
      --config "${CONFIG_FILE}" \
      --timeout 300
    ```

- [ ] **references/scripts参数传递规范** [必选项]：脚本参数传递符合规范
  - 验证方法：检查脚本的参数接收方式
  - 参数传递方式：
    1. 命令行参数（推荐）
    2. 环境变量（用于敏感信息）
    3. 配置文件（用于复杂参数）
  - 错误示例：硬编码参数值、无参数说明
  - 正确示例：
    ```markdown
    脚本调用方式：
    ```bash
    python3 scripts/prepare_reverse_input.py \
      --repo-root "${REPO_ROOT}" \
      --output-path "${OUTPUT_PATH}" \
      --config "${CONFIG_FILE}"
    ```
    ```

##### 7.2.4.4 错误处理检查

- [ ] **Agent工具错误处理** [必选项]：Agent工具调用有错误处理机制
  - 验证方法：检查文档中的错误处理说明
  - 错误处理机制：
    1. **重试机制**：最多重试3次，间隔递增
    2. **降级方案**：失败后使用备用方法
    3. **失败记录**：记录失败原因和上下文

  - 错误示例：无任何错误处理
  - 正确示例：
    ```markdown
    ## 错误处理

    如果Agent工具调用失败：
    1. 重试最多3次，每次间隔10秒、30秒、60秒
    2. 重试失败则使用备用方案（人工审核）
    3. 记录失败原因到日志文件
    4. 交互模式下提示用户
    ```

- [ ] **TaskCreate错误处理** [必选项]：TaskCreate任务有错误处理
  - 验证方法：检查任务失败时的处理逻辑
  - 错误处理方式：
    1. 标记任务为失败状态
    2. 记录错误信息
    3. 依赖任务相应处理
    4. 用户通知
  - 错误示例：任务失败后无任何处理
  - 正确示例：
    ```markdown
    ## 任务失败处理

    如果TaskCreate任务失败：
    1. 通过TaskUpdate标记任务为failed
    2. 在description中记录错误原因
    3. 检查依赖任务是否需要取消
    4. 在交互模式下通知用户失败原因

- [ ] **Bash命令错误处理** [必选项]：Bash命令执行有错误处理
  - 验证方法：检查命令执行失败时的处理
  - 错误处理方式：
    1. 检查退出码（非0则为失败）
    2. 捕获错误输出
    3. 清理临时文件
    4. 记录错误日志
  - 错误示例：命令失败后无任何清理

- [ ] **references/scripts错误处理** [必选项]：脚本有完整的错误处理
  - 验证方法：检查脚本内部的错误处理逻辑
  - 错误处理要求：

    2. 资源清理（临时文件、数据库连接等）
    3. 适当的退出码
    4. 详细的错误日志
  - 错误示例：脚本无异常处理
  - 正确示例：

    try:

        save_result(result, output_file)

##### 7.2.4.5 并发控制检查

- [ ] **并发策略明确** [必选项]：明确subagent的并发执行策略
  - 验证方法：检查文档中的并发控制说明
  - 并发策略类型：
    1. **串行执行**：依次执行，一个完成后再执行下一个
    2. **有限并发**：同时执行最多N个（默认2个，最多5个）
    3. **无限制并发**：同时执行所有（谨慎使用）
  - 错误示例：未说明并发策略
  - 正确示例：
    ```markdown
    ## 并发控制

    本阶段采用有限并发策略：
    - 每轮最多启动2个子Agent
    - 每轮完成后执行/compact压缩上下文
    - 串行处理各轮次
    ```

- [ ] **并发数量合理** [可选项]：并发数量设置合理且有依据
  - 验证方法：分析并发数量的设置原因
  - 并发数量选择原则：
    1. 考虑系统资源限制（CPU、内存）
    2. 考虑Token预算
    3. 考虑任务复杂度
    4. 考虑上下文窗口大小
  - 错误示例：并发数量过大导致资源耗尽
  - 正确示例：
    ```markdown
    ## 并发数量设置

    设置每轮最多2个并发子Agent，原因：
    1. 控制Token使用，避免超预算
    2. 每个Agent处理复杂任务，需要充足上下文
    3. 2个并发在当前资源下性能最优
    ```

- [ ] **资源冲突处理** [必选项]：有处理并发资源冲突的机制
  - 验证方法：检查是否考虑了并发带来的资源冲突
  - 资源冲突类型：
    1. 文件写入冲突
    2. 数据库连接冲突
    3. 临时文件冲突
  - 处理方式：
    - 使用唯一的文件名（时间戳、UUID）
    - 使用互斥锁
    - 任务隔离
  - 错误示例：多个并发任务写入同一文件
  - 正确示例：
    ```markdown
    ## 并发资源管理

    为避免并发冲突：
    1. 每个子Agent使用唯一的输出文件名（包含timestamp）
    2. 最后合并所有输出文件
    3. 临时文件使用进程ID命名
    ```

##### 7.2.4.6 超时控制检查
