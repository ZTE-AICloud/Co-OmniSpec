# 任务生成规则（参考）

主流程见 [SKILL.md]。本文件定义任务格式与组织规则，生成 tasks.md 时严格遵循。

## 关键原则

- 任务按**场景**组织，以支持独立实现与测试。
- **测试任务（强制 TDD）**：每个场景必须包含测试任务，遵循 `/tdd-workflow` 定义的 RED → GREEN → REFACTOR 循环。测试任务在实现任务之前。

## 检查清单格式（必需）

每任务严格遵循：

```text
- [ ] [TaskID] [P?] [Scenario?] 带文件路径的描述
```

**格式组件**

1. **复选框**：以 `- [ ]` 开头
2. **任务 ID**：按执行顺序 T001、T002、T003…
3. **[P]**：仅当任务可并行时（不同文件、不依赖未完成任务）
4. **[Scenario]**：仅场景阶段需要，格式 [S1]、[S2]…；设置/基础阶段无场景标签；完善阶段无场景标签
5. **描述**：含确切文件路径的清晰操作

**示例**

- ✅ `- [ ] T001 根据实施计划创建项目结构`
- ✅ `- [ ] T005 [P] 在 src/middleware/auth.py 中实现认证中间件`
- ✅ `- [ ] T012 [P] [S1] 在 src/models/user.py 中创建用户模型`
- ❌ `- [ ] 创建用户模型`（缺 ID/场景标签）
- ❌ `- [ ] T001 [S1] 创建模型`（缺文件路径）

## 任务组织

1. **来自场景 (spec.md)**：每个场景 P1、P2、P3… 单独阶段；将模型、服务、端点、场景专属测试映射到该场景；标出场景依赖（多数场景应独立）。
2. **来自合约**：每个合约/端点映射到其服务的场景；在该场景阶段的 RED 任务中插入合约测试任务 [P]（强制 TDD）。
3. **来自数据模型**：实体映射到所需场景；若实体服务多场景，放在最早的场景或设置阶段；关系放在对应场景阶段的服务层任务。
4. **来自设置/基础设施**：共享基础设施→阶段 1；基础/阻塞任务→阶段 2；场景特定设置→该场景阶段内。

## 阶段结构

- **阶段 1**：设置（项目初始化）
- **阶段 2**：基础（阻塞先决条件，必须在场景之前完成）
- **阶段 3+**：按优先级顺序的场景（P1、P2、P3…）；每场景内强制 TDD 循环：
  - RED：编写失败测试 → 验证测试失败
  - GREEN：最小实现 → 验证测试通过
  - REFACTOR（可选）：代码优化 → 验证测试仍通过
  - 每阶段为可独立测试的增量。
- **最终阶段**：完善、覆盖率验证（80%+，遵循 `/tdd-workflow`）与横切关注点
