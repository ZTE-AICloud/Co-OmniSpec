# 任务: [FEATURE NAME]

**输入**: 来自 `/changes/[###-feature-name]/` 的设计文档
**前置条件**: design.md(必需)、spec.md(场景必需)、research.md、data-model.md、contracts/

**测试**: 以下示例包含测试任务. 测试是可选的 - 仅在功能规范中明确要求时才包含.

**组织结构**: 任务按场景分组, 以便每个场景能够独立实施和测试.

**棕地实施（章程）**: 任务须优先指向对**既有**文件与符号的修改（具体路径、类/对象、函数/方法）；默认**不**新增源文件、不另起与现状并行的业务逻辑，**禁止空对空新增实现**。若 `design.md` 已论证必须新增文件或新逻辑链，任务描述须与该论证一致并写明目标符号与编辑方式（修改/包装/委托）。

**利旧执行顺序（章程）**: 任务编排时必须遵循 `参数兼容扩展 > 同文件新增函数 > 新增文件`。如果出现新增文件任务，必须在任务描述中引用 `design.md` 的例外论证并标明不可复用原因。

**扩散控制（章程）**: 单个需求默认修改文件数不超过 3 个。若任务合计超过该阈值，须在任务列表开头增加“扩散说明”，列明必要性、风险、回滚点以及压缩改动面的尝试结果。

**波及文件再确认（章程）**: 须对照 `design.md`「波及文件与复用分析」**逐项复核**：仍需要修改的才写入修改类任务；**无需修改**（仅复用、只读、现有已满足）的波及文件**不得**出现「改代码/重构」类任务。若复核结论与设计表不一致，在任务列表首部用简短说明记录（并应回写 `design.md`保持一致）。

## 格式: `[ID] [P?] [Scenario] 描述`
- **[P]**: 可以并行运行(不同文件, 无依赖关系)
- **[Scenario]**: 此任务属于哪个场景(例如: S1、S2、S3)
- 在描述中包含确切的文件路径

## 依赖关系与执行顺序

### 阶段依赖关系

- **设置(阶段 1)**: 无依赖关系 - 可立即开始
- **基础(阶段 2)**: 依赖于设置完成 - 阻塞所有场景
- **场景(阶段 3+)**: 都依赖于基础阶段完成
  - 然后场景可以并行进行(如果有人员)
  - 或按优先级顺序进行(P1 → P2 → P3)
- **完善(最终阶段)**: 依赖于所有期望的场景完成

### 场景依赖关系

- **场景 1(P1)**: 可在基础(阶段 2)后开始 - 无其他场景依赖
- **场景 2(P2)**: 可在基础(阶段 2)后开始 - 可与 S1 集成但应独立可测试
- **场景 3(P3)**: 可在基础(阶段 2)后开始 - 可与 S1/S2 集成但应独立可测试

### 每个场景内部

- 测试(如包含)必须在实施前编写并失败
- 模型在服务之前
- 服务在端点之前
- 核心实施在集成之前
- 场景完成后才移至下一个优先级

### 并行机会

- 所有标记为 [P] 的设置任务可以并行运行
- 所有标记为 [P] 的基础任务可以并行运行(在阶段 2 内)
- 基础阶段完成后, 所有场景可以并行开始(如果团队容量允许)
- 场景中所有标记为 [P] 的测试可以并行运行
- 场景中标记为 [P] 的模型可以并行运行
- 不同场景可以由不同团队成员并行处理

## 实施策略

### 仅 MVP(仅场景 1)

1. 完成阶段 1: 设置
2. 完成阶段 2: 基础(关键 - 阻塞所有场景)
3. 完成阶段 3: 场景 1
4. **停止并验证**: 独立测试场景 1
5. 如准备好则部署/演示

### 增量交付

1. 完成设置 + 基础 → 基础就绪
2. 添加场景 1 → 独立测试 → 部署/演示(MVP! )
3. 添加场景 2 → 独立测试 → 部署/演示
4. 添加场景 3 → 独立测试 → 部署/演示
5. 每个场景在不破坏先前场景的情况下增加价值

### 并行团队策略

有多个开发人员时: 

1. 团队一起完成设置 + 基础
2. 基础完成后: 
   - 开发人员 A: 场景 1
   - 开发人员 B: 场景 2
   - 开发人员 C: 场景 3
3. 场景独立完成和集成

## 注意事项

- [P] 任务 = 不同文件, 无依赖关系
- [Scenario] 标签将任务映射到特定场景以实现可追溯性
- 每个场景应该独立可完成和可测试
- 在实施前验证测试失败
- 在每个任务或逻辑组后提交
- 在任何检查点停止以独立验证场景
- 避免: 模糊任务、相同文件冲突、破坏独立性的跨场景依赖
