# 阶段1：需求分析（场景 → 功能需求）

<!-- 阶段1：将场景分析结果转化为 EARS 语法的结构化功能需求 -->

## 职责

1. 在工程根目录下搜索 `SCN-XXX-*.md` 场景文档并读取为输入。
2. 对场景进行**归类分析**（业务领域、操作类型、角色职责）与**抽象提升**（通用功能模式、共性需求）。
3. 使用 **EARS 语法**将场景转化为功能需求。
4. 输出「功能需求」章节到需求设计文档。

## 输入

- **输入来源**：在**工程根目录**（或 `--path` 指定范围）下**搜索**命名形如 `SCN-XXX-场景名称.md` 的文档（例如 `SCN-013-建立实体关系.md`）。
  - 匹配模式：`SCN-*-*.md`
  - 应用 data.md 中的排除规则（默认排除隐藏目录、`omni-doc/`；不排除 `.cache/`）。

## 输出

- **目标文件**：`{REPO_ROOT}/.cache/reverse/requirements/internal/需求设计.md`（不存在则创建，存在则仅更新「功能需求」章节）
- **填写范围**：仅填写 **功能需求** 章节

## 核心操作：归类与 EARS 转化

### 1. 场景归类分析

- **深度归类**：
  - 按业务领域分组（如：计费、会话管理、接口交互）
  - 按操作类型分组（如：创建、更新、删除、查询）
  - 按角色职责分组（如：用户操作、系统处理、外部交互）
- **抽象提升**：
  - 从具体场景抽象出通用功能模式
  - 识别跨场景的共性需求
  - 归纳系统核心能力

### 2. EARS 语法转化规则

- **Event-driven**：`When [事件], 系统 shall [响应]`
- **State-based**：`While [状态], 系统 shall [行为]`
- **Unwanted**：`If [异常], 系统 shall [处理]`
- **Optional**：`Where [条件], 系统 should [功能]`
- **Ubiquitous**：`系统 shall [基本功能]`

**分层结构**：

```
- [主功能域] 系统 shall 提供XX功能
  - When [具体触发], 系统 shall [具体动作]
  - While [特定状态], 系统 shall [持续行为]
  - If [异常情况], 系统 shall [异常处理]
```

### 3. EARS 质量门

- **来源引用要求**：每个 EARS 句式必须标注来源场景 ID（`[来源: SCN-XXX]`），无来源标注的 EARS 句式不得写入需求设计文档
- **语义正确性**：When/While/If/Where 句式与场景事件类型严格匹配：
  - `When` → 事件驱动型场景（用户操作、外部系统触发）
  - `While` → 状态维持型场景（系统处于某种持续状态时）
  - `If` → 异常/分支型场景（条件判断、异常处理）
  - `Where` → 可选功能型场景（特定条件下才启用的功能）
  - `Ubiquitous` → 系统基本能力（无触发条件，全局有效）
- **不匹配处理**：句式类型与场景事件不匹配时，标注为"待确认 [场景ID]"而非默认通过

### 4. 质量要求

- **完整性**：覆盖所有关键场景功能点
- **一致性**：术语和表达方式统一
- **层次性**：主功能-子功能结构清晰
- **可验证性**：需求可测试、可验证

## Decision Gate

> 判定每条 EARS 需求的覆盖充分性，signal 只能启动调查，不能直接生成强结论。

**Signal candidates**：场景文档全部读取完毕 / 归类分析完成 / EARS 初稿生成完毕

**Required evidence by claim type**：
- `structural`：每个场景的主流程步骤（业务背景 / 触发条件 / 交互流程 / 关键步骤说明）均有对应 EARS 条目
- `relational`：所有参与者（主要参与者）和触发条件均被 EARS 句式覆盖
- `semantic`：EARS 句式类型与场景事件类型匹配（When→事件驱动、While→状态驱动、If→异常）

**Counter-evidence**：
- 场景文档中标记为"后续扩展"或"预留"的章节 → 降级为"待定需求"（不在 completeness ceiling 内）
- 跨场景共性需求无单一来源场景 → 标注来源场景 ID，不得凭空生成

**Decision rules**：
- Signal without evidence → `unresolved`（不输出该需求）
- 覆盖充分（structural + relational + semantic 均满足）→ 生成功能需求条目
- 覆盖不足 → 补充遗漏场景后重新进入 Decision Gate
- 部分覆盖 → `tentative`，标注"待补充 [具体缺口]"

## 注意事项

- 基于实际场景归纳，不添加代码中不存在的功能
- 重点关注功能归类的合理性与完整性
- 需求描述简洁、准确，仅输出需求章节
