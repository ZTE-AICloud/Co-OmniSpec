# Token管理和上下文控制指南

## Token 限制说明

### 模型限制
- **最大上下文长度**：262144 tokens
- **输入 + 输出**：总和不能超过最大上下文长度
- **安全边界**：建议保留至少 10% 的空间作为缓冲

### 实际可用空间
- **建议最大输入**：约 20 万 tokens（保留 6 万 tokens 用于输出和缓冲）
- **单次处理建议**：输入不超过 15 万 tokens，输出不超过 5 万 tokens
- **强制安全限制**：任何单次处理操作的输入tokens不得超过15万tokens

## 上下文管理基本原则

### 1. 阶段级别上下文管理
每个阶段开始时，AI Agent必须主动清空上一阶段的所有上下文信息：

```
【AI Agent内部操作】
1. 忘记上一阶段的所有处理细节
2. 只保留当前阶段必需的状态信息：
   - 阶段名称
   - 缓存目录路径
   - 状态文件路径
3. 重新初始化当前阶段的处理环境
```

### 2. 批次级别上下文管理
在批量处理中，每个批次开始前都必须清空上一批次的上下文：

```
【AI Agent内部操作】
1. 忘记上一批次的所有处理数据
2. 只保留当前批次的必要信息：
   - 批次号
   - 总批次数
3. 重新聚焦于当前批次的处理任务
```

**核心原则**：
- **独立性**：每个级别（阶段/批次）的处理是完全独立的
- **最小化**：只保留必需的状态信息，不保留具体数据内容
- **清空时机**：在开始新级别的处理前，必须清空上一级别的上下文

## Token监控和预警响应

### 实时Token使用意识
AI Agent应该具备持续的Token使用意识：

1. **定期自我检查**：在处理过程中定期评估当前Token使用情况
2. **预判性调整**：在接近Token限制前主动调整处理策略
3. **动态内容压缩**：根据当前Token使用情况动态调整输出内容长度
4. **强制检查点**：在关键处理节点强制检查上下文大小
5. **超限自动处理**：当检测到上下文接近或超过限制时，自动清空上下文并报错

### Token监控机制

请参考 [核心规则文档](core-rules.md) 中的Token管理规则。

### 强制Token检查点
AI Agent必须在以下关键节点强制检查Token使用情况：

1. **阶段开始前**：检查当前上下文大小，如超过10万tokens则强制清空
2. **批次处理前**：检查当前上下文大小，如超过10万tokens则强制清空
3. **文件读取前**：评估文件大小和预计Token消耗
4. **处理过程中**：定期检查上下文大小（建议每处理5个文件检查一次）
5. **批次处理后**：检查当前上下文大小，如超过15万tokens则报错
6. **文件保存前**：检查当前上下文大小，如超过15万tokens则强制清空后再保存
7. **阶段结束后**：检查当前上下文大小，如超过15万tokens则强制清空

## 上下文优化技术

### 1. 按需加载策略
避免将大量数据一次性加载到上下文中：

```
【推荐做法】
❌ 不要这样做：
"让我先读取整个interface-details.json文件内容以便处理..."

✅ 应该这样做：
"我需要处理接口ID为API-001的条目，现在调用read_file工具读取相关部分..."
```

### 2. 引用替代内容
使用引用机制代替直接包含数据：

```
【推荐做法】
❌ 不要这样做：
"根据之前读取的1000行代码内容，我发现..."

✅ 应该这样做：
"根据文件src/api.py中的相关接口定义（文件引用：src/api.py），我分析得出..."
```

## 超大文件处理策略

### 文件预评估机制
1. **文件大小预估**：在读取文件前，先评估文件大小和预估Token消耗
2. **风险分类**：
   - 小文件（<1000行）：正常读取处理
   - 大文件（1000-5000行）：分段读取处理
   - 超大文件（>5000行）：实施特殊处理策略
3. **Token消耗预估公式**：预估Tokens ≈ 文件行数 × 5（平均每行约5个tokens）

### 超大文件特殊处理策略
1. **逐段分析法**：
   - 对于预估Token消耗超过5万tokens的文件，采用逐段分析策略
   - 每次只读取和处理文件的一部分（建议500-1000行）
   - 处理完一段后立即清空相关上下文再处理下一段

2. **内容截断机制**：
   - 对于单个文件超过1万行的情况，实施智能截断
   - 读取前5000行和后5000行，中间部分按需抽样（每1000行抽取100行）
   - 确保关键接口定义不会被截断（通过快速模式识别关键区域）

3. **快速模式识别**：
   - 在处理超大文件前，先使用grep等工具快速识别可能包含接口定义的行号
   - 只重点读取和分析这些关键行附近的上下文
   - 大幅减少实际需要处理的内容量

### 实施细则
1. **强制检查点**：处理超大文件时，每处理1000行必须检查一次上下文大小
2. **自动降级机制**：如发现上下文接近限制，自动切换到更保守的处理模式
3. **上下文清理**：处理完超大文件的每个段落后，立即清空相关上下文信息

## 批次处理中的Token管理

### 批次规划阶段
1. **Token预算分配**：每个批次的预计Token消耗不得超过15万tokens
2. **文件分组策略**：根据文件大小和复杂度合理分组，确保每批Token消耗均衡
3. **批次大小限制**：单个批次处理的文件数量不宜过多，建议不超过20个文件
4. **超大文件隔离**：包含超大文件的批次应单独处理，避免影响其他文件

### 批次执行阶段
1. **批次间隔离**：每个批次处理前必须清空上一批次的上下文
2. **实时监控**：处理过程中持续监控Token使用情况
3. **异常处理**：如发现Token使用接近限制，应立即停止处理并清空上下文
4. **超大文件特殊监控**：处理包含超大文件的批次时，增加监控频率

### 批次完成阶段
1. **上下文清理**：批次处理完成后立即清空该批次的所有上下文信息
2. **状态更新**：及时更新批次状态，为下一批次处理做准备

## 阶段间数据传递的Token优化

### 阶段间数据传递原则

在多阶段编排skill中，阶段间的数据传递需要遵循以下原则以优化Token使用：

1. **使用状态文件代替直接传递**
   - 将中间结果写入状态文件（JSON），而不是保留在上下文中
   - 后续阶段按需读取状态文件，而不是假设上一阶段的数据仍在上下文中
   - 示例：阶段1的结果写入 `{REPO_ROOT}/.cache/reverse/logic_architecture/.cache-status.json`

2. **结构化数据存储**
   - 使用精简的JSON结构存储关键状态信息
   - 避免在状态文件中存储完整的结果内容（如架构识别的详细内容）
   - 只存储必要的信息：确认状态、时间戳、文件路径引用

3. **按需加载**
   - 后续阶段需要使用上一阶段的结果时，显式读取文件
   - 不要假设上下文中有完整的数据副本
   - 使用相对路径引用结果文件，而不是将内容嵌入上下文

### 阶段0→阶段1数据传递

#### 阶段0（缓存与输出目录检查）输出
- 状态文件：`{REPO_ROOT}/.cache/reverse/logic_architecture/.cache-status.json`
- 初始状态结构：
```json
{
  "architecture_identification": {
    "confirmed": false,
    "progress": "pending",
    "timestamp": ""
  }
}
```

#### 阶段1（架构识别）输入
- 读取阶段0的状态文件
- 如果 `confirmed == true` 且产物存在，跳过分析
- 如果 `confirmed == false` 或产物缺失，执行分析

### 阶段1→后续阶段数据传递

#### 阶段1输出
- 主产物：`{REPO_ROOT}/omni-doc/specs/logic_architecture/architecture.json`
- 状态更新：更新 `.cache-status.json` 中的 `confirmed` 字段为 `true`

#### 后续阶段（如 reverse-interfaces）输入
- **不读取上下文中的架构信息**
- **显式读取** `{REPO_ROOT}/omni-doc/specs/logic_architecture/architecture.json`
- 验证文件存在且包含必需字段（architecture_type, modules 等）

### Token优化实践

#### ❌ 不推荐的做法
```
阶段1：
"我已完成架构识别，结果如下：[完整的架构描述]"
"模块列表：['module1', 'module2', ...共100个模块]"

阶段2：
"根据阶段1的架构描述，我需要分析模块间的接口..."
```

**问题**：
- 阶段1的完整结果占用大量上下文空间
- 阶段2需要解析和理解上下文中的架构描述
- 如果架构复杂，结果可能超出上下文限制

#### ✅ 推荐的做法
```
阶段1：
"完成架构识别，结果已写入 omni-doc/specs/logic_architecture/architecture.json"
"架构类型：[类型]，模块数：[数量]"
"状态已更新，confirmed = true"

阶段2：
"开始阶段2，首先读取阶段1的架构结果..."
读取文件：omni-doc/specs/logic_architecture/architecture.json
"已加载架构信息，开始接口分析..."
```

**优势**：
- 上下文只保留关键摘要信息
- 完整数据通过文件传递，不占用上下文空间
- 阶段间松耦合，便于独立测试和维护

### 强制检查点

在阶段切换时，必须执行以下检查：

1. **阶段开始前**：
   - 读取上一阶段的状态文件
   - 验证必要的数据文件存在
   - 检查上下文大小是否需要清理

2. **阶段结束后**：
   - 将关键结果写入状态文件
   - 更新状态字段（confirmed, progress, timestamp）
   - 清空本阶段的详细处理数据

3. **状态文件最小化原则**：
   - 状态文件只存储关键元数据
   - 不存储完整的结果内容
   - 后续阶段需要时显式读取主产物文件
